# v0.14.0

Released: November 24, 2026

This release adds cron jobs: code from one of your NestJS services that runs on a schedule as its own task, on GCP, AWS and Azure. Any scheduled job can now be started on demand, in the cloud or on the local stack.

---

## Cron jobs

A cron job runs code from one of your NestJS services on a schedule, as its own task. The task starts, runs one handler, and exits.

```bash
npx tsdevstack register-cron --service auth-service --name usage-report
```

- `register-cron` creates the handler file. With the service's first cron job, it also creates the entrypoint and the `cron` script. It prints the `infrastructure.json` entry to add.
- You write the handler's `run()` method. It gets the service's secrets, database and Redis.
- Each cloud runs it as a task: Cloud Run Jobs on GCP, ECS tasks on AWS, Container App Jobs on Azure. Each run has its own CPU and memory.
- One run at a time, a timeout that stops the run cleanly, one trace per run, and a final log line with the outcome.
- No retries: a failed run waits for the next scheduled time.

Scheduled jobs that call an endpoint stay as they are. The docs call them triggers. See [Scheduled Jobs](/docs/features/scheduled-jobs#cron-jobs).

## Run a scheduled job now

- `infra:run-cron --job <name> --env <env>` starts a cron job or a trigger now, in the cloud, and reports the run. When a cron job's run fails, it prints the run's last log lines, as `infra:logs` shows them.
- `run-cron <name>` runs it once on the local stack.
- `infra:list-schedulers` shows both kinds, each schedule's state, and each job's last run.

## MCP

- **Secrets:** an agent gives you the command to run in your own terminal: `cloud-secrets:push` for a new environment, `cloud-secrets:set <KEY>` for one key.
- **New tools:** `register_cron`, `run_cron` and `infra_run_cron`. `infra_run_cron` reports a run's outcome without its log lines; logs stay with `get_logs`, which agents must ask you before calling.
- The guide's "Add a scheduled job" covers both kinds.
- `cloud_init` takes an environment, like the command below.

## Improvements

- **`cloud:init --env <env>`** tests only the selected environment.
- **`infra:remove-scheduler`** reminds you to take the job's entry out of `infrastructure.json` only while the entry is still there.
- **Name conversions** (kebab-case, snake_case, CONSTANT_CASE) go through [deep-case-crafter](https://www.npmjs.com/package/deep-case-crafter), a small MIT package with no dependencies of its own. Every name comes out as before. Installing `@tsdevstack/cli` or `@tsdevstack/nest-common` now also installs it.
- **CLI package:** the AWS RDS and load balancer clients install as dependencies instead of being bundled into the CLI.
- **Docs:** GCP setup says to keep every field of the downloaded key in the credentials file, including ones like `universe_domain`.

## Fixes

- **AWS:** a worker of a service with a database gets the service's `DATABASE_URL`. In v0.13.0 workers started without it.
- **GCP:** `infra:deploy-scheduler` for a single trigger gives the scheduler access to the trigger's service.
- **Azure, Kong:** when Azure applied a Key Vault permission late, Kong's deploy could stop after 10 minutes. App Service keeps the denied answer, and restarting Kong doesn't make it read the secret again. The deploy now asks App Service to read Kong's secrets again, and restarts Kong as before only when Azure refuses that.
- **Azure, database jobs:** Azure can count a job's run as failed before its container starts, then run it anyway. A deploy stopped on that. The database setup (`db-init`) and the migration jobs may now start once more after a failed run.

## Upgrading an existing project

**1. Packages.**

```bash
npm install -D @tsdevstack/cli@^0.14.0
npm install @tsdevstack/nest-common@^0.14.0 -w <service>
```

Run the second command for each NestJS service.

**2. Each cloud environment.** Nothing to change. Your scheduled jobs keep running as triggers. To add a cron job, see [Scheduled Jobs](/docs/features/scheduled-jobs#add-a-cron-job).
